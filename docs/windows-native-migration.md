# Переход CrossPost на нативное приложение Windows

Статус: первый прототип 0.1.0 выпущен отдельно как native-v0.1.0; в windows-native разрабатывается 0.2.0-dev с альбомами, порядком медиа и сохранением подтверждений между запросами. Подробности и ограничения — в native/README.md.
Цель: долгосрочное приложение Windows с нативным интерфейсом, автономной установкой
и управляемым обновлением. Текущие Python-релизы продолжают работать до проверки замены.

## Базовые решения

- C# и .NET 10 LTS; перед первым выпуском проверить актуальные сроки поддержки.
- WPF и MVVM: интерфейс без HTML, pywebview и WebView2.
- Основная цель — Windows 11 x64. Поддержку Windows 10 и ARM64 подтвердить отдельно,
  до объявления совместимости. Для ARM64 проверить также ffmpeg, обработку изображений и теггер.
- Self-contained поставка: установленный пользователем .NET/Python не требуется.
  Сначала сборка в папку с собственным runtime; упаковку в один EXE не считать обязательной.
- SQLite сохраняется как формат хранения. Не переносить глобальное соединение из Python:
  короткие транзакции, ограниченное число писателей, обработка блокировок, версионирование схемы.
- Все операции с сетью и файлами — асинхронные, с отменой, прогрессом и явными таймаутами.
  Тяжёлая обработка не выполняется в потоке WPF.
- Разделить пользовательские данные, кэш, модели, временные файлы и файлы программы.
  Прототип использует отдельную папку CrossPostNativePrototype в LocalAppData.

Переход на C# не отменяет браузерную защиту сайтов. WPF убирает WebView2 из окна
программы, но браузерная автоматизация остаётся отдельным механизмом.

## Границы компонентов

| Компонент | Ответственность |
| --- | --- |
| CrossPost.Domain | Пост, черновик, назначения, рейтинг, результат отправки, идентичность сообщения |
| CrossPost.Application | Подготовка и проверка публикации, редактирование, импорт, очередь, команды и запросы UI |
| CrossPost.Infrastructure | SQLite, HTTP, файлы, секреты Windows, адаптеры площадок |
| CrossPost.Desktop | WPF, навигация, редактор, история, календарь, настройки, доступность |
| CrossPost.Worker | Очередь и сбор статистики после закрытия окна, процесс текущего пользователя |
| CrossPost.Updater | Остановка процессов, установка, откат и проверка запуска новой версии |
| CrossPost.Tests | Проверки доменной логики, адаптеров, миграций и восстановления после сбоев |

Не делать Windows Service обязательным: отправка и автозапуск должны работать
без административных прав, в контексте вошедшего пользователя.
UI и Worker используют общий прикладной слой и версионированный IPC по named pipes
с ограничением доступа текущим пользователем. Для одного хранилища допускается
только один владелец выполнения очереди. Собственное окно не требует HTTP-сервера.

## Что переносится из текущего репозитория

| Текущий код | Направление переноса и проверка |
| --- | --- |
| app/api.py, app/web | Команды/запросы прикладного слоя и WPF ViewModels; не копировать монолитный API в окно |
| app/db.py, app/publish/drafts.py | Импорт SQLite, публикаций и черновиков с сохранением идентификаторов и неизвестных полей |
| app/publish/runner.py | Отдельные шаги подготовки, отправки и подтверждения; сохранять результат сразу после отправки |
| app/publish/tg_bot.py | Telegram Bot API через отдельный адаптер; идентификаторы текстового сообщения и медиа сохраняются раздельно |
| app/telegram, app/publish/tg_mt.py | Отдельный прототип MTProto: вход пользователя и бота, альбомы, редактирование, прокси и переподключение |
| app/worker.py, app/publish/schedule.py, app/publish/pipeline.py | Worker с единственным владельцем очереди, журналом выполнения и отменой |
| app/publish/media.py, app/publish/prep.py | ffmpeg как отдельный процесс; проверить преобразования изображений и лимиты платформ |
| app/tagger/jtp.py | PyTorch/timm и .safetensors: эксперимент экспорта ONNX и сравнение результатов |
| app/publish/social_web.py, app/publish/vk_web.py | Отдельный профиль на площадку; ручное завершение там, где сайт препятствует автоматизации |
| app/selfupdate.py, app/apply_update.py | Независимый обновлятор с подтверждением остановки Worker и готовности нового приложения |

Текущие данные включают не только posts.db: publish.json, настройки программы,
шаблоны, ссылки на uploads/превью/экспортированные файлы, состояния очереди,
Telegram-сессии и профили браузеров. Полный список формируется импортёром
по фактическому каталогу данных; нельзя ограничиться копированием одной базы.

## Обязательные технические проверки до масштабного переноса

### Telegram

1. Проверить Bot API на приватном тестовом канале: текст, фото, альбом, видео,
   длинный текст перед альбомом, редактирование и сообщение об отказе.
2. Проверить кандидатную .NET-библиотеку MTProto, например WTelegramClient:
   поддержку бот-авторизации, пользовательского входа, MTProxy/SOCKS,
   альбомов и отмены операций. Проверить лицензию и актуальность сопровождения.
   Выбор библиотеки пока не зафиксирован.
3. Не обещать импорт авторизации Telethon без проверенного формата.
   Допустимый первый вариант — повторный вход в C#-приложении.
4. Сетевой таймаут после отправки означает неизвестный результат.
   Автоматически повторять такую отправку нельзя.

Реальные отправки выполняются только в явно выбранном пользователем тестовом
канале. Модульные проверки и фиктивные HTTP-ответы не заменяют эту проверку.

### Теггер

Текущая модель JTP использует PyTorch/timm и файл .safetensors около 1,7 ГБ.
Прямой загрузки этих весов в ONNX Runtime недостаточно: нужен корректный экспорт
архитектуры и весов, перенос предварительной обработки, порядка тегов и порогов.

Сравнить старую и новую реализацию на одинаковом наборе файлов:
обычные изображения, альфа-канал, разные пропорции и размеры.
Измерить вероятность тегов, порядок результатов, CPU/GPU, память и холодный запуск.
Допуски точности определить до принятия результатов.

Временный вариант — изолированный совместимый процесс теггера с собственным
runtime, поставляемым приложением. Это позволяет убрать требование системного Python,
но не является завершённым отказом от Python. Решение о таком переходном варианте
принимать по результату прототипа ONNX.

## Первый рабочий срез

Первая проверяемая версия не должна выглядеть как готовый продукт со скрытыми заглушками.

1. Нативное окно: «Новый пост», «История», «Настройки».
2. Сохранение и восстановление черновика и выбранных файлов.
3. Настройка Telegram-бота и выбор приватного тестового канала.
4. Предпросмотр фактического текста, подписи, вложений и ограничений.
5. Отправка и сохранение chat_id, всех message_id, отдельного ID длинного текста,
   идентичности бота и результата подтверждения.
6. История с открытием сообщения и редактированием текста/подписи.
7. Перезапуск приложения без потери черновика и истории.
8. Автономная установка на чистую Windows без установленных Python и .NET.

До этих проверок не переносить массово все площадки и статистику.

## Безопасный импорт данных

- Python- и C#-приложения не пишут одновременно в одну рабочую базу.
- Сначала импортировать в отдельное хранилище, исходные данные не менять.
- Делать согласованную резервную копию SQLite через backup API либо после
  подтверждённого закрытия всех писателей; учитывать WAL. Простого копирования
  posts.db при работающем приложении недостаточно.
- Сохранять оригинальные идентификаторы площадки, аккаунта, канала и сообщения;
  номер записи SQLite не является идентификатором внешней публикации.
- Импортировать отложенные задания приостановленными. После проверки назначения
  и времени пользователь явно включает их выполнение.
- Токены в новом хранилище защищаются средствами Windows (DPAPI/Credential Manager).
  Перенос секретов и экспорт резервной копии — отдельные явные действия.
- Сохранить оригинал импортированных JSON и неизвестные поля для будущего переноса.
- До переключения проверить количество записей, даты, пути к медиа,
  альбомы и текстовые варианты. Импорт сам по себе ничего не публикует.

## Порядок дальнейшего переноса

1. Telegram и история — первый рабочий срез.
2. Worker, расписание и независимый обновлятор.
3. Импорт истории, календарь, метрики, объединение и разъединение.
4. Другие официальные API и обработка медиа.
5. Теггер после решения прототипа.
6. Браузерные площадки отдельно, с явным статусом ограничений.

Сначала переносить поведение стабильной версии. Экспериментальные возможности
добавлять по одной после проверки основных сценариев.

## Установка, обновление и выпуск

Рассмотреть готовый механизм обновлений .NET desktop (например Velopack),
но выбрать его после проверки сценария с отдельным Worker, откатом, установкой
без прав администратора и необходимостью portable-варианта.
Для публичной поставки предусмотреть подпись исполняемых файлов и установщика.

Критерии обновления:
- один установщик одновременно, подтверждённая остановка окна и Worker;
- проверка происхождения, версии и целостности пакета;
- готовность нового приложения подтверждается с идентификатором конкретного запуска;
- ошибки запуска доступны в журнале, а не теряются;
- схема данных мигрируется совместимо; откат бинарных файлов не означает автоматический
  откат данных после необратимой миграции;
- проверка на чистой Windows и обновление с предыдущей C#-версии.

## Что ещё не сделано

C#-проекты и первый WPF-прототип созданы. Перенос модели, MTProto, импортёр и полный рабочий срез ещё не реализованы.
Приведённый план не означает проверенной совместимости MTProto, GPU или старых сессий.
Следующая ручная проверка — отправка и редактирование фото/альбома в выбранном тестовом канале. Далее — очередь и расписание, импорт, остальные API. Реальные отправки автоматически не выполняются.
