# Производительность вкладок

Проверено 2026-11-17 на Linux в облачной среде, относительно коммита `614157b` (0.2.17-experimental.23). Оптимизации и первая диагностика опубликованы в 0.2.17-experimental.24. Последующие исправления ниже пока в черновике.

Для воспроизведения в окружении проекта:

```sh
python tests/benchmark_views.py 2000 --profile
```

Сценарий создаёт временную SQLite-базу: один выбранный Telegram-канал, 2 000 публикаций и 2 000 импортированных постов с соответствующими записями сообщений. Посты идут с интервалом 12 часов начиная с января 2024 года. Реальные аккаунты и файлы не используются, внешние публикации подменены пустым списком. После измерений база удаляется. Набор один и тот же до/после; результаты содержат накладные расходы cProfile.

| Серверный расчёт | До | После |
| --- | ---: | ---: |
| Поиск истории с группировкой | 1,15 с | 0,53 с |
| Календарь | 1,07 с | 0,46 с |
| Первая сводка публикаций без сохранённого кэша | 7,78 с | 0,77 с |
| Основная статистика за всё время | 0,21 с | 0,18 с |

Сводка прежде собирала всю историю повторно для каждого месяца среди последних 300 публикаций (шесть месяцев в этом наборе). Теперь группировка общая. Календарь получает пороги успеха и правила ручного объединения один раз, а не на каждой работе. Для сводки норма каждого Telegram-канала считается один раз в рамках запроса; между запросами этот контекст не сохраняется.

При открытии публикаций убран второй запрос `pub_stats_summary`; история, календарь и очередь запрашиваются параллельно. Статистика показывает основные данные, не ожидая завершения дополнительной аналитики и календаря. Обзор трендов появляется до прогноза выбранного тега; ошибка этого прогноза не скрывает готовый обзор.

Браузерный тест специально удерживает ответы дополнительной аналитики и календаря: основной ответ статистики всё равно должен появиться. Проверяется и уход на другую вкладку до завершения этих запросов. Python-тесты защищают количество общих расчётов от роста на каждый пост и проверяют значения статистики и медали месяцев.

Это не время от клика до полной отрисовки на пользовательском Windows. На него также влияют процессор, диск, антивирус, объём превью, число каналов и тегов. Первое построение модели трендов и обучение аналитики остаются вычислительными операциями; полностью устранить любую задержку на любых объёмах этот этап не обещает. Команда без `--profile` измеряет время без профилировщика; для сравнения запускать одинаковый сценарий в отдельных checkout на одной машине.

## Диагностика на пользовательском компьютере

В экспериментальную версию добавлены замеры внутри приложения. Откройте медленные вкладки, затем **Настройки → Диагностика → Сохранить отчёт**. JSON сохраняется в `reports` в папке данных приложения; открывается эта папка. Пришлите файл в чат для разбора. Автоматической отправки нет. Лучше сохранять отчёт сразу после задержки и до перезапуска приложения.

Раздел `timings` содержит сводки (количество, среднее, P95, максимум, ошибки/ожидание) и последние отдельные замеры:

- `server_api`: выполнение метода сервера; `serialize`: очистка данных и подготовка JSON.
- `api`: полное время вызова в интерфейсе, включая получение и разбор ответа. Случайный идентификатор запроса связывает его с серверными замерами; параметры, результат и сообщения ошибок не записываются.
- `render`: синхронное построение/обновление DOM и графиков. Это не время завершения GPU-отрисовки или загрузки всех картинок.
- `navigation`: время после нажатия на вкладку до завершения связанных запросов и обновлений интерфейса. Окно тишины 150 мс нужно только для определения окончания и не включается в длительность. Это диагностическая оценка, не точный показатель «первого полезного кадра». Переход до окончания предыдущей загрузки помечается `ok: false`.
- `longtask`: блокировка основного потока браузера дольше 50 мс, если браузер поддерживает Long Tasks API.
- `resource`: длительность загрузки локальных миниатюр, превью, статики и вложений, если поддерживается Resource Timing. Вместо URL хранится только категория (`thumbnail`, `preview`, `static`, `upload`); внешние ресурсы исключены.

Незавершённые вызовы интерфейса экспортируются с `pending: true`; они не считаются завершёнными ошибками. P95 считается по сохранённым замерам, включая текущую длительность таких вызовов, поэтому это не прогноз времени их завершения. Для блокировок/ресурсов указана вкладка на момент получения записи наблюдателем браузера.

Новые замеры автоматически на диск не пишутся: в памяти не более 2 000 серверных и 1 000 клиентских записей. В текущем черновике серверный буфер разделён на 1 500 важных и 500 рутинных записей, клиентский — на 750 важных и 250 рутинных. Быстрые успешные опросы `info`, `activity`, `tagger_state`, `worker_status`, `news`, `ui_set` длительностью менее 250 мс относятся к рутинным. На клиенте туда же попадают обновления DOM быстрее 50 мс и загрузки ресурсов быстрее 250 мс. Внутри каждого буфера старые записи вытесняются; сводки относятся к сохранённым записям, а не ко всем вызовам с запуска. После перезапуска они теряются. Ранее существовавший ограниченный журнал фоновых задач и замеры памяти остаются в отчёте отдельно; из старых записей при экспорте удаляются тексты исключений. Новые записи содержат только разрешённые идентификаторы, числовые значения и признаки результата; дополнительные поля клиентского отчёта отбрасываются сервером.

Запись одного серверного замера в облачной среде заняла около 1,1 микросекунды при 100 000 записях; на запрос обычно две записи. Это оценка стоимости буфера, а не гарантия такой же нагрузки на любом ПК. Для диагностики не включается тяжёлый профилировщик CPU, не сохраняются скриншоты, HTML или тела запросов.


## Выявленная задержка настроек

В пользовательском отчёте .24 запрос `pub_tg_known` ожидал завершения уже 10,75 секунды. Серверной записи ещё не было, поскольку она создаётся после завершения метода. Код при открытии любых настроек проверял вход в Telegram и получал свежий список каналов. В текущем черновике обычный вызов работает с локальным списком и сохранённым статусом, а обновление запускается отдельной кнопкой. Фоновая проверка соединения остаётся только в разделах Telegram, импорта и соединения; она не включает общий индикатор ожидания и не дублируется, пока идёт предыдущая.

В этом же отчёте быстрые фоновые опросы заполнили оба буфера, поэтому замеры статистики/трендов не сохранились. Разделение буферов защищает важные события от такого потока. Незавершённый переход вкладки экспортируется как `navigation` с `pending: true`.
