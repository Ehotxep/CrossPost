# Работа с CrossPost

## Сначала определить контекст

- Перед изменениями прочитать `STATUS.md`, проверить текущую ветку, `git status` и применимые вложенные `AGENTS.md`. Изучить реализацию нужного сценария, а не делать выводы только по скриншоту или истории чата.
- Python: `app/`, `app/web/`, `core/`, `platforms/`. C# / WPF: отдельная ветка `windows-native`, каталог `native/`. Отсутствие `native/` в Python-ветке ожидаемо.
- Для Python-разработки по умолчанию использовать `experimental`. Стабильные выпуски и C# вести отдельно. Не переносить изменения между направлениями без запроса пользователя.
- Не перезаписывать пользовательские изменения. Если нужны другие ветки, использовать отдельный worktree. Не включать в коммит данные приложения, ключи, браузерные профили или артефакты проверок.

## Выполнение задачи

- Одна задача — один законченный результат с понятными критериями готовности. Не добавлять соседние фичи без запроса.
- Для большой переделки интерфейса сначала показать работающий экран с тестовыми данными либо явно обозначенный макет. Сохранять привычные сценарии Python-интерфейса, если пользователь не попросил их изменить.
- Снимок экрана нужно действительно приложить через доступный интерфейс чата. Путь к PNG сам по себе не означает, что пользователь увидел изображение. Не называть макет снимком работающего приложения.
- Проверять затронутые сценарии. Для публикаций использовать временную базу, подменённый отправитель и локальные DOM-фикстуры. Не отправлять реальные посты и не открывать авторизованные аккаунты для проверки без явного запроса.
- В отчёте указать результат, выполненные проверки и существенные ограничения. Локальный успех не означает успешный CI или проверку на Windows.
- Обновлять `STATUS.md`, когда изменились возможности, ограничения или следующий этап. Не выдавать план за реализованную функцию.

## Проверки Python

Использовать окружение `.venv`; при его отсутствии следовать README. Не менять системный Python.

```sh
python tools/run_tests.py
node tests/web/post-state.test.js
node tests/web/setup-guide.test.js
node tests/web/settings-autosave.test.js
python tests/browser/test_workflows.py
python tests/browser/test_social_web.py
```

Браузерные проверки требуют Chromium из Playwright (`python -m playwright install chromium`). Для установленного Chromium можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE`. Команды и ограничения среды описывать честно; недоступную проверку не считать пройденной. Для C# следовать `native/README.md` в соответствующей ветке.

## Публикация и нумерация

- Изменения по умолчанию оставлять в текущем черновике. Публикация допустима по прямому запросу пользователя. Отправка в `experimental` автоматически запускает выпуск, поэтому `git push` в неё тоже является публикацией.
- Не менять базовую версию, схему нумерации, существующие теги или опубликованные релизы без явно согласованного действия. Разрешение на выпуск само по себе не разрешает перенос тега или произвольный выбор новой базовой версии.
- Экспериментальный workflow добавляет `-experimental.<номер запуска>` к версии из `app/__init__.py` только при упаковке. Пропуски номеров из-за неуспешных запусков допустимы; не исправлять их переносом тегов.
- Перед разрешённой публикацией проверить состав diff, нужные тесты и release notes. После push дождаться CI. Сбой исправить в рамках задачи; не обходить проверки и не ослаблять их для выпуска.
- Считать выпуск завершённым после успешного CI и проверки страницы релиза, архива и контрольной суммы. В финальном ответе дать ссылку и точную версию. Не затрагивать stable/native при экспериментальном выпуске.
